# CNAB Parser

This repository contains a .NET application designed to parse and process CNAB files as described in [this repo](https://github.com/ByCodersTec/desafio-ruby-on-rails).

## Technologies and Tools Used

*   **IDE:** Visual Studio 2022
*   **Backend:** C#, .NET (targeting .NET 9.0), ASP.NET Core
*   **Orchestration:** .NET Aspire
*   **Database:** MS SQL Server
*   **ORM:** Entity Framework Core
*   **Containerization:** Docker, Docker Compose, Testcontainers
*   **Testing Frameworks:** xUnit, NSubstitute, Shouldly

## Project Structure Overview

The solution is organized into several projects, each with a specific responsibility:

*   **`src/CnabParser.AppHost`**: The .NET Aspire AppHost main project, used to define and orchestrate the various services (API, Web, database) within the application.
*   **`src/CnabParser.Api`**: An ASP.NET Core Web API project responsible for exposing endpoints to interact with the CNAB parsing functionality. Endpoint documentation is avaiable at `/docs` path of the running service and allows to make requests interactively.
*   **`src/CnabParser.Core`**: The core domain layer, defining the fundamental business entities (`Store`, `Transaction`) and interfaces for repositories (`IStoreRepository`, `ITransactionRepository`, `IUnitOfWork`) and services (`ICnabFileParser`).
*   **`src/CnabParser.Application`**: The application layer, containing services (`CnabImporterService`) that implement the business logic related to the application.
*   **`src/CnabParser.Infrastructure`**: The infrastructure layer, providing concrete implementations for the interfaces defined in the `Core` layer. This includes data access (Entity Framework Core `CnabDbContext`, `StoreRepository`, `TransactionRepository`, `UnitOfWork`) and the CNAB file parsing logic (`CnabFileParser`).
*   **`src/CnabParser.ServiceDefaults`**: A shared project for common configurations, extensions, and utilities for Aspire-enabled projects.
*   **`src/CnabParser.Web`**: An ASP.NET Core Web application using Razor Pages, serving as a (simple) frontend to interact with the API and display processed CNAB data.
*   **`tests/CnabParser.Api.IntegrationTests`**: Integration tests using Testcontainers to start SQL Server and the `CnabParser.Api` project.
*   **`tests/CnabParser.Application.Tests`**: Unit tests for `CnabParser.Application` project.
*   **`tests/CnabParser.Core.Tests`**: Unit tests for `CnabParser.Core` project.
*   **`tests/CnabParser.Infrastructure.Tests`**: Unit tests for `CnabParser.Infrastructure` project.

## How to Run

You can run this application using either the provided helper scripts or Docker Compose.

### Using Helper Scripts (`run.ps1` or `run.sh`)

The project includes platform-specific scripts to simplify running the application, typically leveraging the .NET Aspire AppHost.

In order to use these methods, the **.Net 9 SDK is required**.

**On Windows (PowerShell):**

```powershell
.\run.ps1
```

**On Linux/macOS (Bash):**

```bash
./run.sh
```

These scripts will build the projects and start the `CnabParser.AppHost` which in turn launches all configured services, including the API, Web frontend, and any dependent databases or services. The Aspire Dashboard will also be launched and will display the current endpoints to interact with the services.

### Using Docker Compose

The application can also be run using Docker Compose, which will build and orchestrate the services as containers.

1.  **Build and run the containers:**
    ```bash
    docker-compose up --build
    ```
2.  **Access the application:**
    Once the containers are up and running.

3.  **Remove the containers:**
    ```bash
    docker-compose down
    ```

## How to Run Tests

In order to run tests, the **.Net 9 SDK is required**. Just run:

```
dotnet test -v quiet
```

Github Copilot (free tier) was used to generate about 90% of the frontend project (`CnabParser.Web`) and also to assist in unit and integration tests creation. It proved to be very handy to build a "first draft" version of tests, which - as all AI generated code - then required some more adjusting and cleaning up.

It also helped in some debugging efforts, mainly focused in issues with generated Docker files, which was first generated by Visul Studio / Aspire internal resources.

## Design Considerations

* A layered design based on Onion Architecture was used here as a knowledge test, since the curret requirements wouldn't probably need that much separation of concerns. Anyway, it serves as a strong foundation in the case for system evolution.

* Some basic care with performance was taken, mainly by trying to reduce memory allocation though the usage of asynchronous streams (`IAsyncEnumerable`) and optimized memory access (`Stream` and `Span`). Again, although not required, it offers a path for more advance work on it if desired.

* Basic logging was added, but metrics weren't. In a production scenario those concens should be tackled with more care.
